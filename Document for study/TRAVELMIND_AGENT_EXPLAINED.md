# TravelMind Agent 工作原理讲解

> 面向目标：解释 TravelMind 当前 Agent 是如何从一句自然语言用户输入，生成工具执行计划、调用实时服务、结合记忆和知识库，最终返回一份旅行规划结果的。
> 本文偏理论说明，不贴具体代码。阅读时建议配合目录 `multi_agent/`、`prompts/`、`tools/`、`services/`、`repositories/` 理解实现。

---

## 1. 需求是什么？

用户不会用数据库字段或 API 参数表达需求，而是会说类似：

```text
帮我规划北京三日游，预算 3000，我喜欢博物馆，不要太累。
```

这句话里同时包含：

1. **任务目标**：生成三日行程。
2. **硬约束**：目的地是北京、预算 3000、旅行天数 3 天。
3. **偏好**：喜欢博物馆。
4. **节奏要求**：不要太累。
5. **隐性信息**：用户期望系统知道天气、景点开放情况、路线距离、预算合理性等。
6. **多轮上下文**：上一轮可能已经说过“我带孩子出行”，本轮不一定重复。

系统不能直接把这句话交给一个大模型就结束。因为旅行规划涉及实时事实和结构化结果：

- 景点是否需要预约。
- 当前天气是否影响户外活动。
- 两地之间交通耗时是否合理。
- 用户是否曾经拒绝过夜爬长城。
- 行程是否符合预算。
- 结果必须能被前端展示、编辑、版本化。

因此，真正的问题是：

> 如何把一句模糊、多意图、包含偏好和实时信息需求的自然语言，转成一个可控、可验证、可恢复、可解释的多步骤执行过程，并最终输出结构化旅行方案？

---

## 2. 传统做法的问题

如果把所有事情都交给单个 LLM，会遇到几个典型问题。

### 2.1 无法保证实时事实准确

LLM 不知道当前天气、今日车次、实时余票、路线耗时、临时闭馆信息。若让它自由生成，很容易编造。

### 2.2 输出难以程序化使用

用户需要前端展示行程、地图、时间轴、版本历史。如果模型只输出一段散文，程序无法可靠地修改“第 2 天第 3 个活动”。

### 2.3 多轮状态容易丢失

旅行规划是长对话过程。用户可能先说目的地，再说日期，再修改预算，最后要求“去掉夜爬长城”。系统必须知道哪些信息属于本次旅行，哪些属于长期偏好。

### 2.4 用户偏好和历史行为难以利用

用户曾经拒绝过夜爬长城、喜欢博物馆、每次旅行偏好慢节奏。如果每次都让用户重复，体验会很差；但也不能把单次临时偏好误写成永久偏好。

### 2.5 外部服务失败时容易失控

天气、地图、铁路服务都可能失败。如果没有统一工具层，失败会扩散到主流程，甚至让模型补写事实。

### 2.6 难以验证行程合理性

时间重叠、预算超支、路线过久、活动过密，这些都应该由确定性代码判断，而不是由模型自己“觉得合理”。

---

## 3. 我们的 Agent 方案

TravelMind 采用的是 **流程角色 + 能力工具 + 结构化状态 + 长期记忆 + RAG + 确定性校验** 的组合方案。

核心思想：

```text
Agent 不等于一个自由对话模型。
Agent 是一个有状态、有分工、有工具、有校验、有记忆的执行系统。
```

整体流程如下：

```text
用户输入
  ↓
Coordinator：恢复会话与身份上下文
  ↓
Feedback：理解偏好、约束、记忆候选
  ↓
Planner：拆解任务，生成工具计划
  ↓
是否信息不足？
  ├─ 是 → Summarizer 追问用户
  └─ 否 ↓
Tool Executor：按依赖执行工具
  ↓
Summarizer：合并结果、错误与解释
  ↓
结构化行程 + 用户回复
```

下面逐步解释。

---

## 4. 第一步：Coordinator 恢复上下文

用户输入进入系统后，第一件事不是马上让模型规划，而是恢复上下文。

Coordinator 解决的问题是：

1. 当前用户是谁。
2. 当前会话是哪一个。
3. 本轮请求 ID 是什么。
4. 上一轮状态如何恢复。
5. 用户这句话应该加入聊天历史。

为什么重要？

因为旅行规划通常是多轮的：

```text
第一轮：我想去北京
第二轮：三天，预算 3000
第三轮：我喜欢博物馆
第四轮：不要安排太累
```

系统必须知道前三轮已经确认过什么，不能每轮都重新问。

---

## 5. 第二步：Feedback 理解“这句话改变了什么”

Feedback Agent 负责区分用户这句话属于哪类信息。

它主要做三件事。

### 5.1 区分长期偏好与当前旅行约束

例如：

```text
我喜欢博物馆。
```

可能属于长期偏好。

但：

```text
这次带孩子，不要太累。
```

属于本次旅行的临时要求。

系统必须区分：

```text
UserProfile：跨旅行有效
TravelRequest：仅本次旅行有效
```

否则会出现错误：

```text
用户这一次带父母要慢节奏
≠
用户永远都要慢节奏
```

### 5.2 提取记忆候选

Feedback 还会判断这句话是否应该沉淀为长期记忆。

记忆分为四类：

1. **语义记忆**：稳定偏好，例如“用户喜欢博物馆”。
2. **情景记忆**：具体事件，例如“用户拒绝过夜爬长城”。
3. **程序记忆**：流程偏好，例如“每次规划前先给三个候选目的地”。
4. **显式记忆**：用户明确说“请记住我喜欢博物馆”。

但不会把所有话都写入长期记忆。低置信度、单次模糊推断、敏感信息都会被拒绝或暂缓。

### 5.3 更新当前旅行状态

如果用户说：

```text
三天，预算 3000
```

Feedback 会更新当前 TravelRequest：

```text
travel_days = 3
budget = 3000
```

这一步结束后，系统已经知道：

```text
用户是谁
当前会话状态
用户长期偏好
本次旅行约束
可能需要沉淀的长期记忆
```

---

## 6. 第三步：Planner 做任务拆解和路由

这是 Agent 最核心的部分之一。

Planner 要回答：

> 为了完成用户本轮目标，需要调用哪些工具？顺序是什么？有没有依赖？是否缺少关键信息？

### 6.1 输入

Planner 会看到：

1. 用户本轮输入。
2. 当前旅行约束。
3. 用户长期偏好。
4. 当前是否已有行程。
5. 可用工具白名单。
6. 长期记忆。

### 6.2 输出

Planner 输出的不是一段自然语言，而是结构化计划：

```text
步骤 1：调用某个工具
步骤 2：调用另一个工具
依赖：步骤 2 依赖步骤 1
参数：每个工具需要什么参数
置信度：系统对计划的把握
缺失字段：如果无法执行，还缺什么
是否需要澄清：如果关键信息不足，先问用户
```

例如用户说：

```text
查一下北京天安门到故宫的公交路线。
```

Planner 可能生成：

```text
步骤 1：geocode 天安门
步骤 2：geocode 故宫
步骤 3：plan_route，依赖 geocode 结果
```

因为公交路线工具要求经纬度，而用户给的是地名。

### 6.3 工具白名单

Planner 不能随意调用系统内任意函数，只能从白名单中选择：

```text
行程规划
行程修改
局部编辑
预算估算
天气查询
汇率换算
POI 搜索
地理编码
路线规划
车站搜索
火车票查询
```

这样可以保证：

1. 模型不能执行危险或未授权能力。
2. 工具参数有 Schema。
3. 每次调用可审计。
4. 系统能解释为什么调用这个工具。

### 6.4 澄清机制

如果用户说：

```text
帮我规划旅行。
```

系统不知道目的地、日期、预算，Planner 可以判断：

```text
needs_clarification = true
```

然后跳过工具执行，直接让 Summarizer 向用户追问。

这避免系统在缺少关键条件时硬编结果。

### 6.5 LLM + 规则兜底

Planner 有两条路径：

1. **LLM 规划**：适合复杂多意图输入。
2. **规则规划**：LLM 不可用或输出异常时兜底。

规则路径虽然不如模型灵活，但能保证基础能力可用，例如：

```text
用户提到天气 → 查天气
用户提到火车票 → 查车票
用户要行程 → 生成行程
```

---

## 7. 第四步：Tool Executor 执行计划

Planner 只负责“想”，Executor 负责“做”。

### 7.1 依赖执行

如果计划是：

```text
geocode → plan_route
```

Executor 会先执行 geocode。只有 geocode 成功，才执行路线规划。

如果前置工具失败，后续工具不会盲目执行，而会返回依赖失败。

### 7.2 上下文构建

执行生成型工具前，系统会构建上下文：

```text
用户本轮输入
当前旅行硬约束
当前行程版本
最近对话
长期偏好
长期记忆
RAG 知识
```

上下文有优先级：

```text
当前用户输入 > 当前旅行约束 > 当前行程 > 最近对话 > 长期偏好 > 长期记忆 > RAG 知识
```

这保证系统不会用过时偏好覆盖用户当前明确要求。

### 7.3 实时工具调用

地图、天气、铁路、汇率等事实必须通过工具获取。

例如：

```text
天气 → Open-Meteo
地图/POI/路线 → 高德 MCP
火车票 → 12306 MCP
汇率 → Frankfurter
```

模型不能编造这些事实。

### 7.4 统一 ToolResult

所有工具返回统一结构：

```text
是否成功
工具名
业务数据
错误码
错误信息
元信息：来源、时间、有效期
```

这样 Summarizer 可以统一处理结果和错误。

### 7.5 工具治理

工具调用经过 Tool Gateway，具备：

1. 审计记录。
2. 缓存。
3. 重试。
4. 错误分类。
5. Provider 健康状态。
6. 熔断保护。

例如相同天气查询在短时间内重复出现，可以命中缓存；外部服务失败时，不会把失败扩散成系统崩溃。

---

## 8. 第五步：实时结果回填行程

工具结果不只用于回答文本，还会回填结构化行程。

### 8.1 POI 回填

搜索到真实 POI 后，可以把：

```text
POI ID
名称
地址
经纬度
来源
```

写入行程活动。

活动状态从：

```text
unknown
```

变为：

```text
verified
```

### 8.2 路线回填

公交/驾车/步行路线结果可以写入两个活动之间的路线段：

```text
起点活动 ID
终点活动 ID
交通方式
距离
耗时
核验状态
```

### 8.3 天气回填

如果某天有雨，系统可以：

```text
追加天气提示
给户外活动标注室内替代建议
```

### 8.4 火车票回填

车次、出发站、到达站、时间、席别可以写入行程的城际交通选项。

---

## 9. 第六步：RAG 提供专业知识

Agent 不能只依赖模型常识。对于景点政策、官方开放时间、用户授权攻略、多日游模板，系统使用 RAG。

### 9.1 知识来源

包括：

1. 官方事实。
2. 用户授权攻略。
3. 多日游模板。

### 9.2 摄取流程

```text
登记来源
→ 内容去重
→ 原始文件保存
→ 结构化切块
→ 元数据标注
→ Embedding
→ 入库
```

不同文档采用不同切块策略：

```text
官方事实：按实体/段落
攻略：按章节
模板：按天
```

### 9.3 多路召回

检索时并行使用：

1. BM25 关键词召回。
2. 向量语义召回。
3. 地理召回。
4. 模板召回。

再用 RRF 融合排序。

### 9.4 引用展示

最终上下文中的 RAG 知识带：

```text
来源名称
来源链接
更新时间
```

模型只能引用这些内容，不能编造来源。

---

## 10. 第七步：Memory 提供个性化

Memory 让系统知道“这个用户是谁”，而不是把每个用户当新用户。

### 10.1 四类记忆

| 类型 | 作用 | 示例 |
|---|---|---|
| 语义记忆 | 稳定偏好 | 用户喜欢博物馆 |
| 情景记忆 | 历史事件 | 用户拒绝过夜爬长城 |
| 程序记忆 | 流程偏好 | 每次先给三个候选目的地 |
| 显式记忆 | 用户明确要求记住 | 请记住我不吃辣 |

### 10.2 记忆写入策略

不是所有信息都写长期记忆。

规则大致是：

```text
用户明确说记住 → 直接写入
稳定高置信偏好 → 写入
具体接受/拒绝/修改 → 写入情景记忆
单次模糊猜测 → 不写
敏感信息 → 默认拒绝
```

### 10.3 记忆检索与冲突处理

检索记忆时，系统会考虑：

```text
相似度
置信度
证据数量
作用域
最近确认时间
```

冲突处理原则：

```text
当前用户输入 > 当前旅行上下文 > 显式记忆 > 语义记忆 > 程序记忆 > 情景记忆
```

例如用户以前喜欢紧凑行程，但这次说：

```text
带孩子，不要太累。
```

系统本次必须遵循慢节奏，不能用旧偏好覆盖当前需求。

---

## 11. 第八步：个性化排序

当行程活动生成后，系统不会只按模型输出顺序展示，而是对候选活动进行可解释排序。

排序特征包括：

```text
用户偏好匹配度
预算匹配度
地点可信度
信息核验状态
类型多样性
历史拒绝记忆
```

如果某个活动命中用户历史拒绝记忆，会被降权。

例如：

```text
用户喜欢博物馆
用户拒绝过夜爬长城
```

排序结果可能是：

```text
1. 故宫博物院
2. 景山公园
3. 夜爬长城（已降权）
```

每个分数都有解释，用户能理解为什么这样推荐。

---

## 12. 第九步：确定性校验

行程不是生成完就结束，还要经过规则校验。

包括：

1. 时间是否重叠。
2. 结束时间是否早于开始时间。
3. 路线是否引用了不存在的活动。
4. 交通耗时是否过长。
5. 一天活动是否过密。
6. 预算是否超支。
7. 活动是否通过外部 POI 核验。

这些不依赖 LLM，而是由普通代码判断。

原因很简单：

```text
确定性规则必须由确定性代码保证。
```

---

## 13. 第十步：版本化与反馈

每次行程生成或修改都会形成版本。

版本记录：

```text
版本号
行程 JSON
修改原因
来源 Agent
创建时间
```

用户可以：

```text
查看历史版本
对比版本
局部修改某个活动
接受或拒绝方案
提交反馈
```

这让行程变成可管理、可追踪、可回滚的对象。

---

## 14. 第十一步：Summarizer 生成最终回复

所有工具执行完成后，Summarizer 合并：

```text
工具成功结果
工具失败信息
澄清问题
行程结构
排序解释
校验警告
来源引用
```

如果只有一个工具结果，直接展示。

如果多个工具结果，分节展示。

如果工具失败，明确告诉用户失败原因，不让模型编造事实。

---

## 15. 为什么这个架构能解决问题？

回到最初的问题：一句自然语言如何变成可靠旅行规划？

我们的方案对应关系如下。

| 问题 | 解决方式 |
|---|---|
| 自然语言模糊 | Feedback 提取结构化偏好与约束 |
| 多轮上下文丢失 | Coordinator + 状态存储 + Checkpoint |
| 不知道调用什么工具 | Planner 生成工具计划 |
| 模型乱调用工具 | 工具白名单 + Schema |
| 需要实时事实 | MCP/API 工具调用 |
| 外部服务失败 | Tool Gateway 统一错误、重试、熔断 |
| 用户个性化 | Memory 系统 |
| 专业知识不足 | RAG 多路召回 |
| 行程不可编辑 | 结构化 Itinerary |
| 行程不可信 | POI/路线/天气回填 |
| 行程不合理 | 确定性校验 |
| 结果不可解释 | 排序特征与来源展示 |
| 结果不可恢复 | 会话状态 + 版本历史 |

## 16. 一次完整请求示例

用户输入：

```text
根据我以前的偏好，帮我规划北京三日游，预算 3000，喜欢博物馆，不要太累。
```

系统过程：

```text
1. Coordinator 恢复用户和会话状态。

2. Feedback 识别：
   - 目的地：北京
   - 天数：3
   - 预算：3000
   - 本次偏好：不要安排太累
   - 潜在长期偏好：喜欢博物馆

3. Memory 检索：
   - 用户喜欢博物馆
   - 用户曾拒绝夜爬长城
   - 用户偏好慢节奏

4. Planner 生成计划：
   - 查询北京天气
   - 搜索博物馆类 POI
   - 生成三日行程
   - 校验行程
   - 估算预算

5. Tool Executor 执行：
   - 调用天气工具
   - 调用高德 POI 工具
   - 构建 RAG/记忆上下文
   - 调用行程生成工具
   - 回填 POI 与路线信息

6. 个性化排序：
   - 博物馆活动提升
   - 夜爬长城降权
   - 慢节奏活动优先

7. 确定性校验：
   - 检查时间重叠
   - 检查预算
   - 检查活动密度
   - 标注未核验信息

8. 保存行程版本。

9. Summarizer 返回：
   - 行程正文
   - 地图数据
   - 天气提示
   - 推荐理由
   - 待核验事项
```

最终用户得到的不是一段不可控的模型输出，而是一份：

```text
结构化
可验证
可编辑
可追踪
个性化
带来源
```

的旅行方案。

---

## 17. 学习时的核心心智模型

理解这个 Agent，最重要的不是记代码，而是记住五个概念。

### 17.1 状态

系统每一步都在读写状态：

```text
用户输入
旅行约束
长期偏好
计划
工具结果
行程
错误
回复
```

### 17.2 计划

Planner 的职责不是回答用户，而是决定“要做哪些动作”。

### 17.3 工具

实时事实和业务能力都通过工具获取，模型不编造。

### 17.4 记忆

Memory 决定系统如何理解用户，但当前用户输入优先。

### 17.5 校验

结构化结果必须经过确定性规则，最后才交给用户。

---

## 18. 一句话总结

TravelMind 的 Agent 不是一个会聊天的模型，而是一个由五类流程角色驱动的规划执行系统：

```text
先恢复上下文，
再理解用户变化，
然后规划工具步骤，
执行实时能力，
回填结构化行程，
结合记忆和知识排序，
最后确定性校验并总结。
```

这套设计的目标是同时获得：

```text
LLM 的语言理解能力
工具系统的实时事实能力
数据库的持久化能力
规则系统的确定性能力
```

因此它能够把一句自然语言，稳定地转换成可执行、可验证、可迭代的旅行规划。
